# Project Commit Story

The following narrative captures how a student could have iteratively developed the PodcastHub platform. Each entry lists the staged files and the commit message that describes the milestone.

| Step | `git add` Selection | Commit Message | Summary |
| --- | --- | --- | --- |
| 1 | `README.md`, `.gitignore`, `.gitattributes`, `LICENSE.md` | `chore: bootstrap Podcasthub workspace` | Captured the project charter, MIT license, and baseline repo hygiene so future commits start on a clean foundation. |
| 2 | `.env`, `docker-compose.yml`, `ngrok.yml` | `infra: provision local dev stack` | Wired Docker Compose with RabbitMQ, MinIO, Postgres, and Redis plus shared environment defaults for one-command local spin-up. |
| 3 | `media-recording-service/src/domain/**`, `media-recording-service/src/application/ports/**` | `feat(recording-domain): define aggregates and ports` | Sketched the DDD core with Recording, Chunk, and Upload models alongside inbound/outbound ports to protect business rules. |
| 4 | `media-recording-service/src/application/services/**`, `media-recording-service/src/adapters/outbound/repository/**`, `media-recording-service/src/infrastructure/config/**`, `media-recording-service/src/infrastructure/dependencies/__init__.py`, `media-recording-service/requirements.txt` | `feat(recording-service): orchestrate recording lifecycle` | Implemented application services, in-memory repositories, and dependency wiring so the recording workflow can run end to end. |
| 5 | `media-recording-service/main.py`, `media-recording-service/src/adapters/inbound/rest/**`, `media-recording-service/src/adapters/inbound/websocket/**`, `media-recording-service/src/adapters/inbound/http/session_routes.py`, `media-recording-service/src/adapters/inbound/http/recording_routes.py`, `media-recording-service/src/adapters/inbound/http/websocket_handler.py` | `feat(recording-api): expose FastAPI surface` | Exposed REST and WebSocket endpoints for session coordination, recording control, health checks, and real-time progress updates. |
| 6 | `media-recording-service/src/adapters/inbound/http/upload_routes.py`, `media-recording-service/src/adapters/outbound/minio_storage.py`, `media-recording-service/src/adapters/outbound/storage/file_storage.py`, `media-recording-service/src/infrastructure/messaging/processing_queue.py` | `feat(storage): wire MinIO uploads and processing queue` | Introduced chunk streaming to MinIO, a resilient storage adapter, and a RabbitMQ publisher that enqueues processing jobs after uploads. |
| 7 | `media-recording-service/src/processors/media_processing_worker.py`, `media-recording-service/src/adapters/outbound/messaging/rabbitmq_publisher.py` | `feat(processing-worker): stitch recordings with ffmpeg` | Added the asynchronous worker that downloads chunks, concatenates them with FFmpeg, uploads processed assets, and fires `recording.processed` events. |
| 8 | `media-recording-service/static/index-multitrack.html`, `media-recording-service/static/recorder-riverside.js` | `feat(demo): add browser recorder prototype` | Delivered a static Riverside-style recorder to exercise multi-track capture, checksum generation, and chunk uploads from the browser. |
| 9 | `media-recording-service/tests/test_api.py`, `media-recording-service/tests/test_recording_service.py` | `test(recording): cover services and happy paths` | Locked in pytest coverage for recording lifecycle use cases and the FastAPI surface so refactors keep behaviour stable. |
| 10 | `media-processing-service/src/**`, `media-processing-service/main.py`, `media-processing-service/requirements.txt`, `media-processing-service/.env.example` | `feat(processing-service): expose job control API` | Stood up the dedicated media-processing FastAPI service with DDD layers, RabbitMQ integration, and REST endpoints for job orchestration. |
| 11 | `podcast-frontend/package.json`, `podcast-frontend/tsconfig.json`, `podcast-frontend/tailwind.config.ts`, `podcast-frontend/src/app/page.tsx`, `podcast-frontend/src/app/create/page.tsx`, `podcast-frontend/src/app/join/page.tsx`, `podcast-frontend/src/app/globals.css` | `feat(frontend): bootstrap Next.js experience` | Scaffolded the Next.js 14 workspace with Tailwind styling and the initial host/guest entry flows tied to environment configuration. |
| 12 | `podcast-frontend/src/hooks/use-recording.ts`, `podcast-frontend/src/hooks/use-webrtc.ts`, `podcast-frontend/src/app/room/**`, `podcast-frontend/src/components/**`, `podcast-frontend/README.md` | `feat(frontend): implement studio WebRTC flows` | Added the WebRTC and recording hooks, live room UI, and participant controls that stream chunks to the recording API with checksum retries. |
| 13 | `media-recording-service/Dockerfile`, `media-recording-service/.dockerignore`, `media-processing-service/Dockerfile`, `media-processing-service/.dockerignore`, `podcast-frontend/Dockerfile`, `podcast-frontend/.dockerignore` | `build: containerise services for compose` | Authored Dockerfiles with Python/Node runtimes, FFmpeg tooling, and lean ignore rules so the full stack runs consistently in Docker Compose. |
| 14 | `ARCHITECTURE.md`, `IMPLEMENTATION_ANALYSIS.md`, `SCENARIO.md`, `COMPILE_REPORT.md`, `Report.tex`, `README.md` | `docs: capture architecture and implementation narrative` | Documented system design choices, scenario walkthroughs, compilation guidance, and refreshed the README with deployment and performance details. |
| 15 | `postman/*.json`, `media-recording-service/postman_collection.json`, `media-processing-service/postman_collection.json`, `ProjectCommitHistory.md` | `docs: publish API collections and commit story` | Finalised the Postman collections for both services and wrote this commit history to support the course deliverable. |

### Tips for Oral Defence
- Walk professors through the domain-first layering (steps 3-5) to show how ports, services, and adapters enforce the hexagonal style.
- Highlight the event-driven pipeline added in steps 6-7 and expanded in step 10 when explaining resiliency and background processing.
- Demo the WebRTC room from steps 11-12 to emphasise how the frontend streams chunks into the recording API and visualises progress.
- Reference the documentation pass in step 14 and this narrative in step 15 when discussing evidence of engineering discipline.
